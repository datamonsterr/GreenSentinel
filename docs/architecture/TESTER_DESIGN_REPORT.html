Tester Simulation Architecture

Status: Proposed design for Epic #130. The 2026-10-04 stakeholder decisions select isolated test storage/sandbox notifications, the existing Workplace layout, 1-second ordinary GPS with selectable slower cadence, and jump, offset/noise and dropout faults. These decisions do not prove runtime delivery or generator acceptance. PRD §11, MVP §8 and glossary define product meaning.

1. System topology and current code evidence

Extend the existing modular monolith. Thin FastAPI routes validate transport; services own persistence/use cases; models own shared schemas; agent nodes invoke scoped tools. Keep simulator state separate from detector/agent state. Do not create a second fraud classifier, seed framework or mobile application.

2. State and graph lifecycle

AgentState is a total-false TypedDict with query, context, analysis, response, error, metadata, messages using add_messages, runtime_context and case_context. The checked-in graph has agent and tools nodes. Tool-call output branches to tools, then returns to agent; otherwise it ends. This simulator adds no graph node or autonomous authority. Current bounded-runtime/tool policies remain applicable; input fixtures and expected evaluation labels never enter detector prompts.

A separate persisted Run state machine handles QUEUED, RUNNING, PAUSED, CANCELLING, COMPLETED, CANCELLED and FAILED. PAUSE suspends simulated time; STOP_MOVEMENT keeps stationary samples and clock advancing. Runtime speed/reroute/fault controls have acceptance and application records, ordered by control sequence. Sample sequence, event sequence and simulation clock are distinct. COMPLETED proves playback completion, not assessment/notification/case success. A failed downstream stage does not rewrite emitted evidence or turn a complete execution into invented no-case proof.

3. Tool and module interfaces

Proposed implementation paths are src/api/test_routes.py, src/models/test_schemas.py, src/services/test_simulation_service.py, src/services/test_simulation_repository.py, and src/services/test_simulation_runner.py. These names are design targets, not existing files. The service owns four deep-module operations: save/preview a definition, accept a run, append a validated runtime input, and read run evidence/results. Route resources in API design adapt those operations; no thin pass-through class is introduced merely to mirror every route.

Validate user/provider/configuration inputs at their seams. A route adapter accepts validated road geometry/provenance; an explicit unavailable response disables start instead of creating a straight line. Route/provider and sandbox-notification adapters are real varying seams (live capability versus deterministic test adapter); do not create abstractions for unobserved hypothetical variation. Database access stays in services/repositories, not agent nodes. Tools receive server-created organization/run/actor context and cannot select operational storage or trusted identities from prompt text. Trap failures as typed stage/error events; they never authorize a sanction.

4. Data flow and durable persistence

  1. Tester opens /test with explicit test permission. Marker selection creates a blank unrestricted definition; routing preview returns validated origin-to-pickup and pickup-to-destination legs, source snapshots and honest metrics.
  2. Save a whole immutable definition revision containing origin/pickup/destination, route snapshot, UTC start time, speed/cadence, planned dialogue, traffic/source settings and explicit faults. Optimistic expected revision prevents lost edits. Future edits create revisions and never rewrite a consumed run.
  3. Start atomically stores an idempotency claim, run, test trip/assignment, immutable effective inputs and outbox intent. Return 202 only after commit. The approximately 60-second target ends at this accepted basic submission; playback and model latency are measured separately.
  4. Durable runner claims a lease/checkpoint, applies ordered controls and emits explicit samples through the existing ingestion use case with test dependencies. Ordinary motion follows road geometry at configured cadence independent of playback speed. Simulated position and reported GPS differ when faults apply; dropout is explicit missingness, not fabricated fixes.
  5. The test-bound queue/worker consumes actual telemetry. Existing assessment/case/assignment use cases write their normal app.* records in the dedicated test database, correlated to run/trip/assignment IDs. Generator/control labels describe authored inputs, never forced classifier answers.
  6. Only actual system notification intents reach a sandbox sink. Persist attempt, recipient, delivery and replies; reconcile UNKNOWN outcomes before retry. If current runtime lacks an integration contract, report UNAVAILABLE and keep the corresponding acceptance item open.
  7. Persist assessment versions, stage evidence, actual case/assignment references and observation window. Stream committed events to both actor windows/results and reload by consistent snapshot plus cursor. Optional AI drafts remain reviewable inputs; they do not send automatically.
  8. /test/workplace mounts the existing analyst layout with test API dependencies. A case link proves neither assignment nor sanction: verify assignment rows and retain separate analyst role/lease/rationale/policy/evidence/audit checks. No mandatory visible TEST case badge is introduced.

Proposed simulator tables in the dedicated database are test_plans, test_definition_revisions, test_runs, test_controls, test_samples, test_events, test_messages, test_notifications, test_result_links, test_idempotency_keys and test_outbox. Existing domain app.* tables remain authoritative for trips/cases/assignments. Use UUIDs, timezone-aware timestamp columns, scalar indexed ownership/status columns, JSONB snapshots for versioned structured payloads, and foreign keys. Enforce uniqueness for (plan_id,revision), (run_id,event_sequence), (run_id,sample_sequence), (run_id,control_sequence) and idempotency scope. Scope foreign keys/queries by organization and owner to prevent cross-run references; index unprocessed outbox rows and ownership/time access patterns. RLS and runtime credentials complement application checks. This is a schema proposal; no migration or shared database mutation is authorized by the document.

Runtime database credentials must not be superuser/BYPASSRLS roles or table-owner connections that silently bypass policy; use transaction-local authenticated organization/owner context and test the actual role. Index referenced ownership/plan/run foreign keys where existing composite indexes do not cover their leading columns. Outbox/runner claims use short atomic transactions and nonblocking locked-row claiming where supported; routing/LLM/notification calls happen outside database lock scope, with durable intent committed first. Pool sizes, statement timeouts and lease recovery limits are configured for test concurrency.

Outbox dispatch and queue delivery are at-least-once. Retries reuse effect identities. A crash between persistence/enqueue/ack must reconcile the checkpoint and committed event ledger without duplicate trip, sample, reply or notification effects. Retain idempotency tombstones and immutable source evidence under the API retention/recovery contract. Exact input replay creates a new run; model output may vary and its versions are recorded.

5. Decisions, alternatives and metric semantics

ADR-015 recommends additive /test interfaces, dedicated test infrastructure and reusable domain use cases over shared operational flags, a new classifier or an in-memory demo. Cost: additional durable records, injected dependencies and environment verification. Benefit: arbitrary composition, reproducible inputs and honest system outcomes without production contamination.

Use 1-second ordinary GPS as the selected design baseline, selectable slower cadence and explicit JUMP/OFFSET_NOISE/DROPOUT. Numeric profile/rate/duration limits remain proposals pending representative normal, stall, reroute and fault validation. Do not reuse the older corpus's ten-second jitter/scaled cadence as this default. Density-to-speed mapping requires an accepted version and independent segments; historical traffic is source-backed only when provider/time/coverage/licensing is verified. No vendor is selected here.

Radius is proposed as pickup-centred geometric placement, distinct from road distance. Source/time/version accompany ETA; planned simulation duration differs from historical/simulated traffic ETA. DAVI reuses feature-engineering window/reference semantics; insufficient movement remains unavailable, and legitimate one-way travel can have negative alignment. Metric/profile proposals require reviewer and Tester acceptance; synthetic results do not validate detection accuracy.

6. Security and boundary protection

A URL prefix is not a security or storage boundary. Use dedicated test Postgres, isolated Redis/queue/vector namespaces, graph checkpoints, object storage and notification sink credentials. Missing/mismatched configuration fails closed; do not fall back to operational URLs or fixture cases. Validate resource/account identity at startup without printing secrets. Explicit egress/sink configuration prevents real customer/driver delivery. Read-only policy/reference material may be shared only through a reviewed adapter that cannot write operational resources.

All simulator operations require authenticated Tester permission and ownership even outside production. Existing permissive development identity behavior is not sufficient. Separate simulated actor maps from analyst permissions; Tester-only tokens fail analyst actions in the test Workplace. Provider/API keys remain server-side; sanitized errors carry request/run/effect IDs, not tokens or raw prompts. Apply configured payload, execution, connection and provider quotas. Authorization is checked on every REST read/mutation and stream reconnect/revocation; UI filters are never the only gate.

API specification

Tester Simulation API Design

Status: Proposed contract for Epic #130, not implemented endpoints. Frontend /test calls canonical backend /test/api/v1. Existing /api/v1 contracts remain in API_SPECIFICATION.md. The test router has no root or /api/v1/test alias.

Interface and authorization

All routes require a verified principal and explicitly provisioned tester permission, including development environments. A missing principal fails 401; missing permission fails 403. Organization and plan/run ownership are checked server-side; scoped absence returns 404. Existing auth helpers contain development fallbacks; the proposed test dependency must reject those fallbacks. User-supplied actor IDs, database targets, environment flags or privileged roles cannot select credentials or grant permissions.

The Tester owns plans/runs and operates server-mapped simulated DRIVER and PASSENGER identities. A Passenger reply is not an analyst decision. Analysts receive normal assignment/review permissions separately in the isolated environment. Case creation and assignment occur only through actual system assessment; there is no force-create-case endpoint. /test/workplace reuses the existing layout with an injected test client and test-scoped case APIs. Tester permission alone never grants claim/adjudication rights.

Wire conventions and validation

Use camelCase JSON, UUID identifiers, RFC3339 UTC timestamps ending in Z, metres, metres/second and seconds. Coordinates are named latitude/longitude at authoring; route GeoJSON uses [longitude, latitude]. Reject non-finite numbers, invalid coordinate ranges, naive times, negative speed, out-of-route segments and unknown enum values. HTTP request types exclude server-generated identity/hash/result fields. Provider responses are validated before consumption. Adapters explicitly translate to existing snake_case TelemetryEventEnvelope; never change that contract to match this new namespace.

The stakeholder selected 1-second ordinary GPS cadence, selectable slower cadence, and JUMP, OFFSET_NOISE, DROPOUT. Proposed initial engineering bounds are cadence 1–60 seconds, speed 0–50 m/s, at most 100,000 samples per run, 5,000 characters per message, and 200 messages per definition. These are design proposals, not measured acceptance or policy facts. Fault displacement/noise/duration bounds, definition byte limit, concurrency/rate quotas and run duration caps must be frozen in a versioned capability profile after representative-trip validation. /capabilities reports the configured limits; unsupported values fail 422 with field details. A missing accepted profile disables execution, rather than permitting unlimited input.

Lifecycle, metrics and errors

QUEUED becomes RUNNING after durable worker claim. PAUSE accepts only RUNNING and produces PAUSED after application; RESUME accepts only PAUSED. CANCEL accepts QUEUED/RUNNING/PAUSED, enters CANCELLING and then CANCELLED. Natural playback completion becomes COMPLETED; permanent execution error becomes FAILED. Terminal execution cannot restart; replay creates a new run. STOP_MOVEMENT keeps the simulation clock and stationary GPS advancing, unlike PAUSE. Speed/reroute/fault controls are applied only at the next acknowledged sampling boundary; conflicts reject 409. Changes to past offsets or already emitted samples reject 422. Results may remain PENDING after COMPLETED until the real detector/assignment stage resolves.

Map radius is a proposed pickup-centred geometric placement constraint, not a road-distance rule. Show named distance references and units. Preview and run use the same metric/profile versions. DAVI follows feature_engineering.py: approach-window distance-weighted directional alignment toward pickup; segments beginning within 20 metres are excluded, insufficient evidence remains null/unavailable, and negative DAVI on legitimate road geometry does not prove intent. Per-point inspection references the segment/window used; it does not invent a standalone DAVI for one fix. Producer samples never fabricate precomputed detector features. NO_CASE_OBSERVED requires a persisted completed assessment and observation window; empty lists, timeouts or unavailable detectors are not no-case proof.

Idempotency and durable recovery

The client generates one key per intent, retained across retries, including JWT refresh. Atomically claim a unique (organization,principal,method,normalizedPath,key) record with canonical request hash, resource reference and state in the same transaction as the durable mutation/outbox. Exact replay returns stored original status/body; changed payload rejects 409; in-flight duplicate rejects 409 with Retry-After. Server-created idempotency keys are invalid substitutes for client intent.

Proposed minimum retention is 7 days and never shorter than the longest configured queue/recovery retry window. Keep key/hash/resource tombstones afterward until the corresponding run is deleted by authorized retention, rejecting old keys with KEY_EXPIRED rather than treating them as new. A timeout/worker crash after an external effect yields UNKNOWN and a durable reconciliation task; query/reconcile by event/message identity before retrying. Unique sample/event/command identities and sandbox notification deduplication protect at-least-once delivery. Never infer “failed to send” merely because the response timed out.

Streaming, pagination and retention

Create run snapshots and their event cursor atomically. Reconnect with last durably applied event sequence; the UI deduplicates by run/event identity, replays before tailing, and never treats transient connection loss as a failed run. Persisted event sequence and sample sequence are separate: explicit GPS dropout leaves an explained sample/time gap without losing event-log ordering.

Expired cursor returns 410 CURSOR_EXPIRED with the snapshot resource reference. Snapshot recovery preserves full persisted evidence; cursor expiration cannot silently delete required run artifacts. Proposed event-retention baseline is 7 days, with immutable run artifacts retained under separately approved storage policy. Bearer-authenticated fetch streaming permits JWT refresh without credentials in URLs. Authentication expiry closes the stream and triggers fresh token plus cursor resume; authorization revocation stops access. Slow clients are disconnected when the bounded buffer fills, then resume by cursor/poll. Heartbeats are transport keepalives, not durable assessment events. GET /events is the polling fallback. Limits, heartbeat interval and reconnect/backoff thresholds are configured, versioned and tested; no unbounded queue or browser memory buffer.

Sources and test handoff

Architecture, isolation ADR, test strategy and manual/UAT tests define implementation proof. FastAPI supports router prefixes/dependencies; its background task guidance motivates durable workers for this long-running slice. Next.js route groups do not create URL prefixes: use a real app/test segment. UI explanations follow WAI tooltip guidance with non-hover alternatives.

Manual test plan

Manual test: Tester trip simulation

This runbook is executable against a dedicated /test frontend and /test/api/v1 backend using isolated test storage and sandbox notifications. It is not a production or hosted acceptance claim until the environment and evidence are recorded.

Preconditions

Use a disposable migrated database, unique Redis/queue namespace, test vector collection, sandbox notification adapter, two simulated principals (Passenger and Driver), and a Tester account. Start the API and Next.js app on dedicated ports. Confirm the selected environment, run namespace, auth roles, provider flags, and notification sink before creating data. Capture run_id and test commit.

Core walkthrough

  1. Open /test, create a trip on the actual map route renderer, choose origin, pickup, destination, speed, historical time, and route. Confirm ordinary GPS defaults to 1 second; select slower cadence within the proposed intervalS range 1–60 seconds and record validation against a representative trip. Hover/select the route and each actor/control icon; confirm tooltip text, units, references and keyboard/focus equivalents. Expected: plausible route and temporal positions are shown; no hidden default GPS or zero metric appears.
  2. Start the one-minute UAT timer on blank authoring (before the first map selection), review and edit every plan field, then submit an accepted run. Stop the timer at accepted run submission; playback and detection-response latency are excluded. Save/reload and compare the saved plan byte-for-byte at the contract level. Expected: complete plan and provenance reload; the captured timing is a real UAT observation, not a fixture claim.
  3. Start the run. Change speed, pause, resume, stop, and reroute. Inspect the event timeline. Expected: ordered controls are persisted; pause/stationary is distinct from stopped movement; original plan and prior evidence remain immutable.
  4. Open the Passenger and Driver windows on the left. Send replies from each actor, receive a system notification, and inspect recipient, sender, timestamp and run lineage. Expected: only the intended sandbox actor receives each message; notification/provider failure is visible and retryable.
  5. Add two route segments with different congestion levels/densities. Request historical traffic for a supported and unsupported time/provider. Expected: source/time is shown when available; unsupported is explicit; simulated congestion is labelled and never presented as observed history.
  6. Trigger a normal assessment, then repeat with insufficient movement, the selected jump, offset/noise and dropout fault modes, provider failure and worker interruption. Use the configured numeric bounds for each fault and record them; representative-trip validation and API-owner approval are required before treating bounds as accepted. Expected: observed outcomes are respectively case/pending or no-case/unknown/failed as applicable; no fabricated assessment, assignment or notification is emitted.
  7. If a case is assigned, open it through the existing Workplace layout. Verify the assignment, evidence, provenance, messages and assessment are present without requiring a visible TEST badge. Attempt Analyst adjudication as Tester. Expected: existing claim, rationale, evidence snapshot, policy version and authorization checks still apply.
  8. Refresh the page and reconnect the event stream with a cursor. Repeat one request with the same idempotency key, then reuse it with changed payload while a duplicate is in flight. Expected: exact replay returns the stored response with no duplicate effect; changed-payload and in-flight duplicates return 409; expired cursor and token refresh are explicit recoverable states; crash/timeout remains auditable as unknown.

Failure and isolation checks

Run two namespaces and two actor pairs concurrently. Confirm plans, vector results, Redis events, cases, notifications and Workplace assignments never cross. Attempt unauthorized role/API access and direct production notification configuration. Expected: auth/RBAC denies access and the sandbox guard prevents operational delivery. Delete only the disposable namespace after evidence capture and verify unrelated rows remain.
