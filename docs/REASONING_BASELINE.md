# REASONING BASELINE

## Purpose

How-to and reference guide for the deterministic forensic reasoning baseline. It defines the frozen input/output contract, runnable benchmark, metrics, evidence rules, and extension path. It is an engineering benchmark guide. It makes no policy or legal claim.

## Scope

The baseline maps structured telemetry and case facts to a category, confidence, and grounded evidence. It covers synthetic cases only. It excludes production policy decisions, calibrated probabilities, hidden chain-of-thought, and live telemetry ingestion.

## Input Contract

Each case supplies facts only. The input contains no scenario name or expected label. Typical fields include outage state, GPS quality, reported location status, stationary duration, passenger cancellation, and completion status. Exact field names and validation constraints are authoritative in [`ForensicInput`](file:///C:/Users/admin/OneDrive/Desktop/AI_20K_PJ/GreenSentinel/src/models/forensic.py).

## Decision Rules

Rules execute in this order:

1. Outage, degraded GPS, or missing telemetry: `insufficient_evidence`, confidence `0.0`.
2. Reported mock location: `ERR-05`, confidence `0.9`.
3. Stationary duration at least 180 seconds plus a trip cancelled by the passenger: `ERR-02`, confidence `0.8`.
4. Otherwise, completed case: `no_violation`, confidence `0.7`.
5. Otherwise: abstain.

The thresholds are illustrative synthetic benchmark thresholds. Confidence is a ranking signal for this baseline, not a calibrated probability.

## Output and Evidence

Every output must validate against the exported `ForensicOutput` schema. Evidence is an object with:

| Field | Meaning |
|---|---|
| `source` | Name of an input field |
| `value` | Value read from that input field |
| `description` | Concise rationale tied to the observed value |

Evidence must be grounded in the case input. A rule-triggering output should include the fields that triggered the rule. `insufficient_evidence` should identify the unavailable or degraded input. The output may include a concise evidence rationale. Do not store or request private chain-of-thought.

## Run the Benchmark

From the repository root:

```powershell
python -m eval.reasoning_baseline
```

The runner loads the frozen mock cases, calls `assess_case`, validates each result with Pydantic, exports the output schema, computes benchmark metrics, and writes:

- [`eval/results/reasoning_baseline.json`](file:///C:/Users/admin/OneDrive/Desktop/AI_20K_PJ/GreenSentinel/eval/results/reasoning_baseline.json)
- [`eval/results/forensic_outputs.json`](file:///C:/Users/admin/OneDrive/Desktop/AI_20K_PJ/GreenSentinel/eval/results/forensic_outputs.json)
- [`eval/results/forensic_output.schema.json`](file:///C:/Users/admin/OneDrive/Desktop/AI_20K_PJ/GreenSentinel/eval/results/forensic_output.schema.json)

The committed golden set must contain at least three synthetic cases and must retain `input`, `expected_category`, and `required_evidence` for each case.

## Benchmark Metrics

The result summary reports:

| Metric | Definition |
|---|---|
| `category_accuracy` | Correct predicted category divided by case count |
| `schema_validity` | Outputs passing `ForensicOutput` validation divided by case count |
| `evidence_grounding` | Evidence items whose `source` exists in the corresponding input and whose value matches that field, divided by evidence items |
| `required_evidence_recall` | Required evidence items present in the output evidence, divided by required evidence items |

Metrics are averaged per case. The runner rejects an empty dataset; the output contract rejects empty evidence. An empty required-evidence list has recall 1.0. Report actual generated scores from the result artifact, not estimates.

## Extension Procedure

1. Add frozen held-out cases without exposing their expected labels to the model or decision function.
2. Keep the same Pydantic contract and metric definitions so scores remain comparable.
3. Add a rule only when its input fields, threshold, expected category, and required evidence are represented in a synthetic case.
4. Re-run the benchmark and inspect both JSON outputs and schema validation.
5. For an LLM implementation, require concise evidence rationales grounded in input fields. Evaluate those rationales as evidence; do not capture private chain-of-thought.

## Limitations

- Synthetic cases do not represent production traffic or edge-case prevalence.
- Illustrative thresholds do not establish policy, legal, or operational criteria.
- Confidence values are not calibrated probabilities.
- Rule ordering can dominate outcomes when several signals coexist.
- Evidence grounding checks field/value linkage, not causal truth.
- Held-out coverage, distribution shift, latency, and human review quality require separate evaluation.
